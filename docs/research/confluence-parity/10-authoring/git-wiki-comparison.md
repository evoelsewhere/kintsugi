# Authoring and structure: how Git-backed and Markdown-first wikis solve it

> Research page. The authoring constraints of the Confluence parity pack were settled by the architects (see `open-questions.md`): working state in Postgres and reviewed text in Git, a page id in front matter, an order list in the folder's `README.md`, attachments in `_attachments/`, Markdown first and rich text later. This page checks those decisions against how six tools that keep pages as files or as Markdown solve the same problems. Only public documentation was read; where a claim comes from a third party it says so. The features compared are the rows of `feature-matrix.md`.

## The tools

| Tool | What it is | Pages are |
|---|---|---|
| Wiki.js | A wiki application with an optional Git storage module | Pages kept by the application and synchronised with a Git repository by the module |
| GitBook | A documentation product with a two-way Git sync | Markdown files and a `SUMMARY.md` table of contents |
| Docusaurus | A static documentation site generator | Markdown files in a `docs/` folder |
| MkDocs with awesome-nav | A static site generator and a navigation plugin | Markdown files and a `.nav.yml` per folder |
| BookStack | A wiki application | Rich-text or Markdown pages in books and chapters |
| Obsidian | A local Markdown note editor | Markdown files in a folder (a vault) |

Outline, which was on the list, is left out: the pages found were third-party tools and not Outline's own documentation, so nothing could be cited.

## Comparison

| Concern | What the tools do | Evidence |
|---|---|---|
| **Page tree and order** | Docusaurus orders by a `sidebar_position` in each page's front matter or by a `_category_.json` in each folder, and says number prefixes in file names are possible but metadata is preferable because renumbering breaks relative links. awesome-nav keeps the order in one `.nav.yml` per folder, a list of file and folder names, with a `...` entry standing for all the rest; its predecessor used a `.pages` file the same way. GitBook keeps the order in one `SUMMARY.md` for the whole book, and its documentation warns that the file has to match the real paths and titles. BookStack has a fixed hierarchy of shelves, books, chapters and pages. | [Docusaurus autogenerated sidebars](https://docusaurus.io/docs/sidebar/autogenerated); [awesome-pages plugin](https://pypi.org/project/mkdocs-awesome-pages-plugin/); [GitBook Git Sync](https://gitbook.com/docs/getting-started/git-sync) and a [third-party description of its layout](https://www.mintlify.com/docs/migration/gitbook.md); [BookStack content overview](https://www.bookstackapp.com/docs/user/content-overview) |
| **Move and rename** | Docusaurus gives a page an id from its path and a URL from the id, and recommends an explicit `slug` so that renaming a file does not change its address; it finds broken links only when the site is built. Obsidian updates the links to a note when the note is renamed or moved, but not when files are moved while it is closed. | [Docusaurus, create a doc](https://docusaurus.io/docs/create-doc); [Docusaurus routing](https://docusaurus.io/docs/advanced/routing); [Obsidian internal links](https://help.obsidian.md/links); [a request about files moved while it is closed](https://forum.obsidian.md/t/auto-update-links-for-files-moved-while-obsidian-is-closed/91670) |
| **Attachments and images** | GitBook, in a synced repository, keeps uploads in one `.gitbook/assets/` folder (per a third-party migration guide). GitBook syncs in both directions: edits in its editor go to Git and commits in Git come back, with merge conflicts resolved in Git. BookStack's export gives the original Markdown when the page was written in the Markdown editor and a conversion otherwise. | [Wiki.js Git storage](https://docs.requarks.io/storage/git); [Wiki.js storage framework](https://docs.requarks.io/dev/storage); [GitBook Git Sync](https://gitbook.com/docs/getting-started/git-sync); [BookStack export and import](https://bookstackapp.com/docs/user/export-import) |

| **Export** | BookStack exports a book, chapter or page as HTML, PDF, Markdown, plain text or a portable ZIP with its attachments and images; third-party reports say its PDF can differ from the screen. The file-based tools need no export, since the source is Markdown. | [BookStack export and import](https://bookstackapp.com/docs/user/export-import) |

## What it says about each decision

| Decision of the constraints thread | Verdict | Why |
|---|---|---|
| **Q1 Drafts in Postgres, publish is one write** | Confirmed | Wiki.js synchronises with Git in batches (every five minutes by default, with a force-sync); none of the pages read describes a commit per keystroke. GitBook's two-way sync commits what the editor saves, which is the model Kintsugi rejected because of history noise and writer-queue load; its documentation names merge conflicts as the cost. |
| **Q2 Review by pull request by default** | Neither confirmed nor challenged | None of the pages read describes a review step on wiki edits as a default; GitBook and Wiki.js synchronise with a repository. Kintsugi's pull request flow is stricter than all of them and no evidence shows it too slow; the cost is a pull request per publish. |
| **Q3 Attachments beside the page in `_attachments/`** | Challenged mildly | GitBook uses one central folder. A central folder avoids copies of an image used by several pages and keeps a page's folder free of binaries; a folder beside the page keeps the link relative, moves the files when the page moves and lets a space be exported alone. Kintsugi's own choice follows from the move operation: a central folder would need link rewrites for every image of a moved page. Worth a line in ADR-0096. |
| **Q4 Markdown source first, rich text behind a round-trip test** | Confirmed | BookStack, whose pages can be rich text, gives the original only for pages written in Markdown and converts the others on export. A conversion is what the round-trip test is meant to catch. |
| **Q5 Page id in front matter, relative links rewritten on move** | Confirmed | Docusaurus gives no stable address without an explicit slug and finds broken links only at build time, which is late; Obsidian rewrites links on a move but fails when the move happens outside the tool. Both argue for what Kintsugi chose: a stable id in the file, and the rewrite in the same write as the move, not in a client that may be closed. |
| **Q6 A space is a folder of the one repository** | Challenged | Wiki.js asks for a dedicated repository and cannot use a subfolder; a shared repository invites collisions. Kintsugi's repository is shared with job outputs, and the writer's one-write-at-a-time rule and `expectedHash` are the protection. The risk is worth a test with a runtime write racing a page publish. |
| **Q7 Markdown export and print first, server PDF later** | Confirmed | BookStack, whose export includes PDF, is reported to give PDFs that differ from the screen; a converter is a maintenance cost. |
| **Q10 Order list in the folder's `README.md`** | Confirmed | awesome-nav and Docusaurus keep order in one file per folder; Docusaurus advises metadata over number prefixes because renumbering breaks links. GitBook's single `SUMMARY.md` for the whole book is the cautionary case: it must be kept equal to the paths by hand. Kintsugi's rewrite of the parent's list on a move avoids that. awesome-nav's `...` (the rest, after the listed ones) matches the decision that unlisted entries follow the list. |

## Findings to carry back

- **Keep the writer in charge of the order list and the links.** Every tool that keeps order or links in a separate file (`SUMMARY.md`, a `.nav.yml`) has the risk that the file and the paths drift. The decision to rewrite the parent's `order:` and the inbound links in the same write as the move is the answer, and a link check is the safety net (AUT-53).
- **Show a page's address by id.** Docusaurus's advice to set a slug shows what happens without one. AUT-02 and Q5 cover it.
- **A shared repository needs a race test.** One acceptance test for the writer: a page publish and a runtime job output racing on the same repository, with the page's `expectedHash` current and then stale.
- **Say why attachments are beside the page.** ADR-0096 should record the central-folder alternative and why it was not taken.
