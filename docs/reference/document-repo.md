# Document repository

> Status: ✅ decided ([ADR-0019](../decisions/0019-workspace-repo-write-path.md), [ADR-0028](../decisions/0028-remove-rulebook-single-document-repo.md), D29, D48). File formats are still drafts.

Each project has exactly one document repo. It holds everything except code ([ADR-0007](../decisions/0007-git-as-source-of-truth.md)): the manifest, the AS-IS analysis, the TO-BE documents, the work items and the project's standards. It is created from the [starter template](../../templates/document-repo/) or joined when it already exists ([build a project](../guides/build-project.md)).

## Layout

```
kintsugi.yaml                 # project manifest: document repo, applications and their repos, pipelines
assessment/<app>/scorecard.md
assessment/<app>/...           # understanding-phase artifacts (ADR-0027): INTENT.md, PREFLIGHT.md, ASSESSMENT.md,
                              #   topology.json, BUSINESS_RULES.md, DATA_OBJECTS.md, RULE_REVIEWS.json, DELTA_CATALOG.md,
                              #   SECURITY_FINDINGS.md, MODERNIZATION_BRIEF.md, VERIFICATION.md
knowledge/as-is/<app>/...     # AS-IS documents (generated + human-written); the understand stage (ADR-0031) writes:
knowledge/as-is/<app>/<module>/<unit>.md   #   one AS-IS specification per unit
knowledge/as-is/<app>/README.md            #   index; architecture.md, data-model.md, integrations.md beside it
knowledge/as-is/<app>/traceability.md      #   unit <-> rules <-> files <-> dependencies <-> findings (+ traceability.json)
knowledge/to-be/...           # TO-BE documents
architecture/adr/NNNN-*.md    # project ADRs
standards/conventions/        # target conventions (plain Markdown)
standards/mappings/           # legacy construct or UI pattern -> target, one file per mapping
standards/review-rules.md     # the rules reviewers enforce
plugins/kintsugi/             # built-in member plugin, generated by Kintsugi (never edited by hand)
plugins/<plugin>/             # project member plugins, Claude Code plugin format (ADR-0015)
units/<app>/<module>/<unit>.md  # one file per work item; frontmatter = state (ADR-0012); proposed by understand
tasks/<work-item-id>.md       # task packs
reviews/<work-item-id>/...    # gate-reviewer records
deliverables/<phase>/...      # detail designs, test reports, ... (large binaries: D31)
golden/<unit>/cases/<id>/     # golden-master cases for compare: inputs + legacy outputs, listed in golden/<unit>/cases.json
golden/<unit>/fresh/<id>/     # fresh inputs invented by verify, listed in golden/<unit>/fresh-cases.json
runs/<unit>/<run-id>/         # small reports per run (EQUIVALENCE.json, test-runs.json, test and canary logs); raw actuals are not committed
.claude-plugin/marketplace.json         # generated marketplace (Claude Code, Copilot CLI)
.github/plugin/marketplace.json         # generated marketplace (Copilot CLI)
.agents/plugins/marketplace.json        # generated marketplace (Codex)
```

`standards/` and `plugins/` have no schema and no maturity: a standard applies once it is merged, and every valid plugin is published to the project marketplace.

## Repository model

| Group | Role | Count | Who writes |
|---|---|---|---|
| Project | `document` | exactly one, declared at project level | Kintsugi (`kintsugi-bot`) and members, through PRs or `autoCommitPaths` |
| AS-IS (per application) | `legacy` | any number: legacy code | Nobody through Kintsugi; read-only |
| AS-IS (per application) | `legacy-data` | any number: schemas, dumps, reference data | Nobody through Kintsugi; read-only |
| TO-BE (per application) | `target` | any number, each with `component: <name from the architecture>` | Members only; the runtime never writes |

The document repo holds both the AS-IS analysis and the TO-BE documents; the portal shows it under TO-BE.

Further rules: each target repo implements a different component of its application, a repository appears at most once per project, and a document repo belongs to one project only (legacy and target repos may be shared between projects). Projects are managed in the portal (**Administration → Projects**) and stored in Postgres; the repositories are the ones registered in **Settings → Git** ([data model](data-model.md#projects-and-their-repositories)).

## `kintsugi.yaml`

```yaml
schemaVersion: 1
project:
  id: billing-modernization
  name: Billing modernization
document:
  server: github-main              # Git server id registered in the installation
  path: org/billing-docs           # clone URL path relative to the server's base URL, without .git
unitKinds: [screen, api, batch-job]
applications:
  - id: billing-web
    name: Billing web
    disposition: refactor          # 7R
    pipeline: refactor             # a built-in pipeline, or one declared under `pipelines:`
    repos:
      - {server: github-main, path: org/billing-web-legacy, role: legacy}
      - {server: github-main, path: org/billing-db, role: legacy-data}
      - {server: azdo-internal, path: Billing/_git/billing-web, role: target, component: web}
      - {server: azdo-internal, path: Billing/_git/billing-api, role: target, component: api}
  - id: payroll-batch
    name: Payroll batch
    disposition: rearchitect
    pipeline: payroll-rearchitect
    repos:
      - {server: gitlab-onprem, path: legacy/payroll-cobol, role: legacy}
      - {server: gitlab-onprem, path: payroll/payroll-java, role: target, component: payroll-service}
pipelines:
  - id: payroll-rearchitect
    appliesTo: {dispositions: [rearchitect]}
    phases:
      - id: migrate
        perUnit: true
        stages:
          - {id: implement, performer: {member: [dev]}}
          - {id: review, performer: {agent: gate-reviewer}}
          - {id: approve, performer: {member: [core-team]}, gate: G4}
autoCommitPaths:
  - units/**                      # state changes, committed by kintsugi-bot
  - tasks/**
  - knowledge/**/generated/**
policy:
  harnesses: [copilot, claude-code]
  requireCommitTrailer: true
```

Schema (`validateManifest` in `packages/domain`, `parseKintsugiYaml` in `packages/manifest`; every problem is reported with its path, e.g. `applications[0].repos[1].component`; unknown keys are problems):

| Key | Required | Content |
|---|---|---|
| `schemaVersion` | yes | `1` |
| `project` | yes | `id` (kebab-case), `name`, optional `description` |
| `document` | yes | The document repo: `server` (Git server id), `path` |
| `unitKinds` | yes | Non-empty list of unit kinds, without duplicates |
| `applications` | yes | List (may be empty). Each: `id` (kebab-case, unique), optional `name`, `disposition` (7R), optional `pipeline` (id), `repos` |
| `applications[].repos` | no | Each: `server`, `path`, `role` (`legacy`, `legacy-data` or `target`; `document` is not allowed here), `component` (required for `target`, unique per application, forbidden otherwise). A `server` + `path` pair appears once in the file, the document repo included |
| `pipelines` | no (default `[]`) | Each: `id` (unique), optional `appliesTo.dispositions`, non-empty `phases` (`id`; `category` required for a custom phase; optional `perUnit`; non-empty `stages` with `id`, `performer` = `{agent: <id>}` or `{member: [<roles>]}`, optional `gate`), optional `gates` |
| `autoCommitPaths` | no | Globs (`**` spans folders, `*` and `?` stay within one segment); default `units/**`, `tasks/**`, `knowledge/**/generated/**` (ADR-0019). The writer reads them from `kintsugi.yaml` on the default branch, and uses the defaults when the file is missing or invalid |
| `policy` | no | `harnesses` (default: the built-in member harnesses), `requireCommitTrailer` (default `true`) |

`path` is the repository's clone URL path relative to its server's base URL, without `.git`: `https://dev.azure.com/acme/Billing/_git/web` on a server with base URL `https://dev.azure.com/acme` gives `Billing/_git/web`; `git@github.com:org/app.git` gives `org/app`. Pipeline ids are not yet checked against the built-in pipelines (their list is an open follow-up of ADR-0028).

**Rendered and published from the portal.** The project page shows, and `GET /api/admin/projects/:id/kintsugi.yaml` returns, the manifest rendered from the project's state in Postgres: project, document repo, applications and their repos. `unitKinds`, `pipelines`, `autoCommitPaths` and `policy` show defaults until the portal manages them. **Publish kintsugi.yaml** (`POST /api/admin/projects/:id/kintsugi.yaml/publish`, permission `projects.manage`) hands the rendered file to the [writer](#write-path): `kintsugi.yaml` is not an auto-commit path, so it arrives as a pull request from `kintsugi/<user>/<write-id>`. The project page lists recent writes with their status and pull-request link (`GET /api/admin/projects/:id/document-writes`).

## Write path

Only the worker's writer (`services/orchestrator`, [ADR-0019](../decisions/0019-workspace-repo-write-path.md)) commits to the document repo. Callers (the API, runtime job completion) enqueue a `document-write` job; the writer handles one write per document repository at a time:

1. Resolves the project's repository with role `document` and its server credential; fetches its mirror.
2. Validates the files: relative paths without `..`, `.`, empty or `.git` segments, no symbolic links; at most 500 files, 5 MiB per file, 50 MiB per write. A violation fails the write.
3. Commits paths matching `autoCommitPaths` to the default branch, and the other paths to `kintsugi/<agent-or-actor>/<job-id>` (the write id when there is no job). A write marked `reviewAll` (the `understand` stage, whose work items are proposals linked to the specifications of the same pull request, [ADR-0031](../decisions/0031-understand-stage-as-is-specification.md)) puts every path on the branch, auto-commit paths included.
4. Pushes fast-forward only: on a rejection it fetches, rebases and retries (4 attempts in all); a rebase conflict fails the write. It never force-pushes and refuses any ref other than the default branch and `kintsugi/*`.
5. Opens a pull request from the `kintsugi/*` branch with the server's token: GitHub, GitHub Enterprise, GitLab, Gitea and Azure DevOps. `plain-git` servers, servers authenticated by SSH key, and Bitbucket (no adapter yet) keep the pushed branch.
6. Records the outcome in `workflow.document_write`: `committed`, `pr-opened`, `unchanged` (the files were already identical) or `failed` with a redacted error ([data model](data-model.md#document-writes)).

## Commit conventions

Every commit by Kintsugi has the **commit identity** as author and committer and carries the trailers that apply to it. The commit identity is an installation setting that admins with `git.manage` set in the portal (Settings → Git → Commit identity): a name and a plain email address, by default `kintsugi-bot <kintsugi-bot@kintsugi.invalid>` (`.invalid` never delivers mail). Use an address the Git server maps to the bot account to link the commits to it. The writer reads it for each write, so a change applies from the next write on; an unset or unusable value falls back to the default. The table below writes `kintsugi-bot` for whatever identity is set.

| Who | Branch | Author | Trailers |
|---|---|---|---|
| Kintsugi worker (PR) | `kintsugi/<agent>/<job-id>` | `kintsugi-bot` | `Kintsugi-Job: <id>`, `Kintsugi-Agent: <agent>@<version>` |
| Kintsugi worker (auto-commit) | default branch | `kintsugi-bot` | same as above |
| State change on behalf of a user | default branch (`units/**`) | `kintsugi-bot` | `Kintsugi-Actor: <user>`, `Kintsugi-Unit: <unit-id>` |
| Change published by a user from the portal (e.g. `kintsugi.yaml`) | `kintsugi/<user>/<write-id>` (PR) | `kintsugi-bot` | `Kintsugi-Actor: <user>` |
| Members | own branches | the member | `Assisted-by: <harness>` when AI-assisted |
| Standards and plugins changes | own branches, PR reviewed by the architect | the member | — |

Provenance records the document repo commit an artifact was produced against.

## Unit files

One file per work item ([ADR-0012](../decisions/0012-work-items-as-files-in-git.md)). The frontmatter is the unit's state. Postgres indexes it for the board and queries, and can rebuild the index from Git. Example: [`templates/document-repo/units/_example.example.md`](../../templates/document-repo/units/_example.example.md).

| Field | Description |
|---|---|
| `id` | `<application>/<module>/<unit>`, stable |
| `application`, `module`, `kind`, `title` | Identity; `kind` is one of the `unitKinds` in `kintsugi.yaml` |
| `wave`, `pilot`, `complexity` | Planning |
| `phase`, `stage`, `status` | Progress. `status`: `pending`, `in-progress`, `awaiting-review`, `approved`, `rejected`, `blocked`, `done`, `skipped` |
| `assignee`, `harness` | Who works on it, and with which member harness |
| `dependsOn` | Unit ids (used for leaves-first ordering) |
| `source`, `target` | `{repo, paths}` lists in the legacy (read-only) and target repos |
| `links` | Task pack, AS-IS doc, mappings (paths under `standards/mappings/`), business rules, pull requests |
| `gates` | Per-gate result: `status`, `by`, `at`, review record path |

**Proposed by the `understand` stage** ([ADR-0031](../decisions/0031-understand-stage-as-is-specification.md)): one file per unit the stage derives from the map, with `phase: discover-assess`, `stage: understand`, `status: pending`, `complexity` from size, `dependsOn` from the traceability matrix, the legacy `source` paths and `links.asIs` / `links.businessRules`. They arrive in the stage's pull request, not as auto-commits; a unit that already has a file is left unchanged.

**Rules**:
- **Write path**: state changes go through the Kintsugi API (portal, CLI, MCP, runtime agents). The API validates the actor's effective access-role permissions and the allowed transition, updates the index, and the worker commits as `kintsugi-bot` with `Kintsugi-Actor`.
- **Direct edits** are allowed only through PRs. They are validated on sync; invalid changes are flagged and not indexed.
- **History** is Git history; there is no separate transition log.

## Resolved by ADR-0019

- **Dedicated repo, or a `kintsugi/` folder inside an existing repo?** A dedicated document repo per project.
- **Which paths are auto-committed by default?** `units/**`, `tasks/**`, `knowledge/**/generated/**` (`autoCommitPaths` in `kintsugi.yaml`); everything else lands on `kintsugi/<agent>/<job-id>` branches as pull requests.
