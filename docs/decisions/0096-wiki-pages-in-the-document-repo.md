# ADR-0096: Wiki spaces and pages are Markdown in the document repository; collaboration state is in Postgres

- Status: Proposed (amends [ADR-0042](0042-markdown-only-document-repo-by-bounded-context.md) decision "Markdown only" for page attachments; extends the layout of [ADR-0051](0051-document-repo-layout-legacy-and-modern.md))
- Date: 2026-11-02
- Decision register: D110

## Context

Projects want a Confluence-like wiki: spaces, a page tree, pages with links, images and labels, version history, comments, mentions, watches and notifications, edit restrictions, templates and search. Kintsugi already has most of the storage it needs. Each project has one document repository that holds everything except code ([ADR-0028](0028-remove-rulebook-single-document-repo.md)), in Markdown with front matter ([ADR-0042](0042-markdown-only-document-repo-by-bounded-context.md)), laid out in numbered folders ([ADR-0051](0051-document-repo-layout-legacy-and-modern.md)). Git is the source of truth for documents ([ADR-0007](0007-git-as-source-of-truth.md)), Postgres is the only datastore ([ADR-0010](0010-postgres-only.md)), every commit goes through one writer ([ADR-0019](0019-workspace-repo-write-path.md)), and the Brain indexes one branch of the repository for people and members' agents ([ADR-0091](0091-brain-vectorless-tree-index.md)).

The wiki must decide where each of its objects lives. Some are reviewed text that people and agents cite; some are conversation, per-person state or access rules that change many times a day. Putting conversation in Git floods the history and needs a pull request per comment; putting page text in Postgres makes a second source of truth the Brain cannot cite. The research behind this decision, with its sources, is in the Confluence parity research pack: [data model](../research/confluence-parity/40-architecture/data-model.md).

## Decision

1. **The wiki is a view over the project's one document repository.** There is no separate wiki store or repository. A page is a Markdown file; the page tree is the folder tree; a page with children is a folder whose `README.md` is the page itself.
2. **Spaces are folders.** The numbered roots (`00-project/`, `01-standards/`, `02-architecture/`, `03-transition/`) and each application under `10-applications/` are system spaces; people make free spaces under a new root `20-spaces/<space>/`. A space's home page is its `README.md`, whose front matter gives `title` and `key` (an uppercase short name used as the page-id scope). Paths are built only in `packages/domain/src/document-layout.ts`. Stage-written documents are shown read-only or edited by pull request only; `_generated/`, `restricted/`, `plugins/`, `scratch/`, hidden folders and identifier ledgers are never editable in the wiki.
3. **Reviewed page content is in Git, in front matter and Markdown.** Front matter carries `id`, `title`, `summary`, `labels` (a short list), `owner`, `status` (`archived` joins the existing status words), `template`, `type: template` on template files, and, on a folder's `README.md` only, `order` (a list of entry names giving the manual order of the folder's pages). The body is CommonMark with GitHub tables, Mermaid, GitHub alerts for panels and fenced `kintsugi-<macro>` blocks for dynamic macros, stored as the macro and never as its output. Templates are Markdown under `01-standards/page-templates/` and `<space>/_templates/`.
4. **Pages have stable ids.** A page's id is front matter `id: PAGE-<KEY>-0001`, the shape of [ADR-0075](0075-compact-stable-document-reference-ids.md), written on its first save in the portal. A counter per project and scope in Postgres allocates it; the counter is a cache that can be rebuilt from the ids the Brain has indexed, and the writer refuses a publish whose id another path already defines. Links in pages are relative Markdown links; a move or rename is one write that renames the file and rewrites inbound links and the parents' `order` lists. Portal permalinks use the id.
5. **Version history is Git history.** A version is a commit that changed the file; its message is the version comment; a minor edit carries the trailer `Kintsugi-Minor: true`; a portal publish also carries `Kintsugi-Actor` and `Kintsugi-Page`. The author of a portal publish is the actor of its `workflow.document_write`, matched by commit (the review watch records the merge commit it saw). Restore is a new write of the old text. Nothing is copied into Postgres.
6. **Attachments are files beside the page.** This amends ADR-0042's Markdown-only rule for one folder name: `_attachments/` beside a page may hold PNG, JPEG, GIF, WebP and PDF files (SVG only sanitised or as a download), at most 5 MiB per file and 50 MiB per write, the writer's existing caps. No Git LFS, no object storage, no bytes in Postgres except a file pasted into an unpublished draft (below). Everything else in the repository stays Markdown.
7. **Collaboration and per-person state are in Postgres, keyed by page id.** In the `knowledge` schema, with a `wiki_` prefix: `wiki_id_counter`, `wiki_draft` (one per user and page: Markdown, base commit, base hash, revision), `wiki_draft_attachment` (bounded bytes of a draft, deleted at publish), `wiki_restriction` (edit and publish restrictions per path prefix and principal), `wiki_comment` (footer and inline, with a text-quote anchor at a commit; `open`, `resolved`, `orphaned`), `wiki_mention`, `wiki_watch`, `wiki_reaction`, `wiki_favourite`, `wiki_recent`. `monitoring.wiki_page_view` keeps daily view counts without user ids; `core.notification` is the inbox for every source. A page without an id is keyed by its path until its first save, and re-keyed when Git reports it renamed. Rows are deleted with the project.
8. **Viewing has one boundary: Project Access to the whole repository** ([ADR-0062](0062-coding-agent-context-and-project-access.md)). No view restriction is offered on a page in Git, because members' clones and the Git server hold the text anyway. Editing and publishing can be restricted per space, folder or page path. Content some project members must not see is not a wiki page in Git.
9. **Every publish is one document write.** Autosaves stay in Postgres. A publish is a write of kind `page` with the draft's base hash; it is a pull request by default, a direct commit only on paths the manifest lists and for holders of a publish permission (the editing and publishing flow is the subject of ADR-0098).

## Consequences

- The wiki needs no new datastore, repository or index; pages render in any Git viewer, members' agents read them through the Brain with citations, and a member's clone holds the whole wiki.
- People can write a page by pull request from their own editor, and the wiki shows it after the merge like any other page.
- Comments, watches and notifications never make commits, so history stays readable; they are lost with the database, unlike pages, and are covered by the Postgres backup.
- The repository grows with images; Git keeps every version of every attachment. The per-file cap and the allowlist bound it; a project with many large binaries needs another home for them.
- A page cannot be hidden from one member who has Project Access. Projects that need that keep such content outside the document repository until a restricted-page store is decided.
- Version numbers are computed from Git on request, so a long history costs a bounded `git log` per view, not storage.
- Follow-up work: layout functions and their reference pages, migrations for the `wiki_*` tables and their permission codes, the writer's `page` kind with delete and rename operations, the attachment allowlist in the writer and a raw-file route, Project Access on the portal's document routes, and the Brain changes of [ADR-0097](0097-brain-indexes-wiki-pages.md).

## Alternatives considered

- **Pages in Postgres, Git as an export.** Rejected: two sources of truth, the Brain could no longer cite `path:lines@commit`, members' agents and clones would not see pages, and reviews would leave Git.
- **A separate wiki repository per project.** Rejected: ADR-0028 decided one document repository per project; a second one splits standards from the pages that explain them and doubles the mirror, writer and Brain configuration.
- **Comments and labels in Git** (a sidecar Markdown file per page). Rejected for comments: a commit or pull request per comment, merge conflicts between commenters, and history noise. Labels are in Git because they are reviewed page metadata that the Brain filters on.
- **A per-page `order` number.** Rejected: a reorder changes every sibling file; one list in the parent's `README.md` changes one file, as Docusaurus and MkDocs do.
- **Attachments in Postgres or object storage.** Rejected: a second source of truth that Git viewers and clones do not see, or a new infrastructure dependency ([ADR-0006](0006-self-hosted-package.md)).
