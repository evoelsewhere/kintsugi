The idea

Repair it with gold, so it comes out more valuable.

Kintsugi is the Japanese art of mending broken pottery with gold. The old piece is not thrown away. Legacy systems deserve the same: monolith to modular, with the knowledge preserved.

How it works

From legacy code to a reviewed build, one unit at a time.

The screens below show a sample project. Every document you see is a plain Markdown file in your Git repository.

01 · Understand

Turn a legacy codebase into a catalog you can choose from.

Assessment groups source files into catalog items without language-specific parsers. An AI plan proposes what to understand first. You select, and the runs do the rest.

  • Catalog derived from the code and curated by an analyst agent
  • Items ordered by calls, shared data and cycles. Advice, never a gate
  • Several selections in flight at once, and a failed run resumes where it stopped

Sample data

02 · Specify

Specifications that cite their evidence.

For each selected unit, Kintsugi writes what it does, the business rules it enforces, the data it touches and the risks it carries. Every statement points to the file and line it came from.

  • Rules, data objects, findings and trace per unit, with a human verdict on each rule
  • Security review built in, with the limits of the review recorded
  • Traceability from legacy source to design, code and tests

Sample data

03 · Build and review

Builders keep their assistant. Reviewers stay independent.

Once a design is merged, a developer implements and tests the unit on their own machine with Claude Code, Copilot or Codex. The runtime then reads the merge request against the unit's rules, design and your standards.

  • The build command records which unit, which merge request and which commit
  • Findings return as a document in a pull request. The merge request is never changed
  • Plugins are distributed, permitted and monitored per project and member

Sample data

04 · Govern and measure

See what AI is doing, and what it costs.

Spans per job, turn and tool call. Tokens, cache reads and cost by project, agent and model. Gates G0 to G4 record who decided what, on which evidence.

  • Per-agent model binding, allowlists and budgets
  • Append-only audit log enforced by database triggers
  • Role-based access with project-scoped member tokens

Working model

The brain works on the server. The hands stay on your machines.

Kintsugi separates platform intelligence from implementation, and keeps people in charge of every decision.

1

The runtime reads, never writes your code

A generic agent kernel runs one job at a time in its own workspace. Source is read-only; results arrive as pull requests on the document repository.

2

Members build with their own assistant

Existing licenses, existing habits. The Kintsugi CLI and a local MCP bridge give them project context and the plugins their project permits.

3

Git is where both sides meet

Specifications, designs, standards and plans are Markdown in one repository per project. People start stages and decide gates.

Delivery pipeline

One pipeline. Five gates. A person behind each.

Every phase ends at a gate: a decision backed by evidence in Git. A project can declare its own phases, stages and design sets.

Architecture

Runs on your infrastructure, on one host.

A self-hosted Docker Compose package. No Kubernetes, no multi-tenancy, and no extra infrastructure to run.

  • An app container (API, member API, portal) and a worker (orchestrator, git writer, runtime). Only the app is exposed
  • PostgreSQL with pgvector is the only datastore. Git is the source of truth
  • Any LLM provider, including on-premises, configured in the portal and bound per agent
  • Credentials are encrypted at rest and decrypted per job, in memory only
Security and governance

Built on the assumption that legacy code is hostile.

Legacy repositories can contain prompt-injection payloads. Kintsugi treats them as untrusted input and states the limits of its own controls plainly.

Isolated job workspaces

Source mounted read-only. Writes confined to the job's output and scratch directories. Scripts run with a cleared environment.

Credentials stay encrypted

LLM keys and Git tokens are encrypted in Postgres, never returned by the API, and decrypted per job in memory only.

Restricted data, audited

Sensitive findings are stored encrypted. Every read is recorded before the content is returned.

Tool allowlists

Each agent gets only the kernel tools it needs, path-confined. MCP servers are registered by administrators.

Append-only audit

Stage runs, configuration, access changes and gate decisions are recorded. Database triggers refuse updates and deletes.

Cost control

Model allowlists, per-agent bindings and per-job limits on turns and cost, with telemetry by project, agent and model.

Get started

Connect a developer in three commands.

Sign in to a project, set up your AI client, and install the plugins your project permits. Then build from the assistant you already use.

Install guide → View on GitHub 
# sign in to a project in your browser
kintsugi login billing-core

# set up your AI clients with the local MCP bridge
kintsugi init

# add a plugin your project permits
kintsugi install plugin modernize

# then, in Claude Code, Copilot or Codex
/modernize:build
